### 2.1 로그의 시스템 식별자와 제시 순서

대화에서 썼던 A/C는 임시 호칭이다. 코드 enum, API, 원본 로그, 파일명, 분석 CSV에 A/C를 시스템 식별자로 사용하지 마라. 다음 의미가 명확한 고정 ID를 사용하라.

| `interface_id` | 의미 |
| --- | --- |
| `smartphone_touch` | 스마트폰 2축 터치 조이스틱 |
| `mr_ballgrip` | Quest 패스스루와 손 추적 BallGrip |

`difficulty_id`는 프레이밍 난이도를 별도로 식별한다. 제시 순서는 `interface_order` 배열과 1부터 시작하는 `period_index`로 별도 기록하라. 예를 들어 `interface_order: ["smartphone_touch", "mr_ballgrip"]`에서 MR의 `period_index`는 2이다. MR을 먼저 수행해도 `interface_id`는 그대로이며 `period_index`만 1이 된다.

표시명은 UI용이며 ID를 대신하지 않는다. 참가자 익명 ID도 시스템 ID와 별개다. 블라인드 분석용 재코딩이 필요하면 별도 파생 자료와 매핑으로 처리하고, 재현 가능한 원본 로그의 시스템 식별자는 보존하라.

## 5. 구현해야 할 공통 계약

### 5.1 표식 검출과 성공 판정

초기 구현은 고정된 내용의 인쇄 QR을 대상으로 한다. 실제 프레임 판독과 판정 상태기를 분리하고, 상태기에 시각·검출 결과를 주입할 수 있게 하여 재생·테스트가 가능하도록 하라.

검출 결과에는 다음이 필요하다.

- 원본 `frame_id`, 원본 촬영 시각 또는 실제로 제공되는 원본 시각, 수신·판독 완료 시각. 촬영 시각이 없으면 없다고 표시하고 수신 시각을 촬영 시각으로 꾸미지 말 것.
- 해독된 표식 내용, 네 모서리 좌표, 영상 해상도.
- 영상 중앙 기준의 표식 중심 편차, 표식 사각형 면적/영상 면적.
- 처리 시간, 새 프레임 여부, 데이터 유효성·나이.

정규화 예: `ex = (cx - image_width/2) / image_width`, `ey = (cy - image_height/2) / image_height`, `area_ratio = polygon_area / (image_width * image_height)`. 분모와 허용범위 단위를 문서에 고정하라.

성공은 다음 조건이 새로운 프레임에서 지정 시간 동안 유지될 때 한 번만 발생시킨다.

1. 해독 내용이 목표 표식과 정확히 일치한다.
2. 중심 편차가 설정된 수평·수직 허용범위에 들어간다.
3. 면적 비율이 설정된 최소·최대 범위에 들어간다.
4. 영상이 최신이며 허용 프레임 간격을 만족한다.
5. 정지를 과제 조건에 포함한 경우 공통 중립 명령 조건을 만족한다. 명령 중립은 물리적 정지 실측과 구별한다.

시행 시작 전 프레임이나 이전 시행의 유지 상태를 재사용하지 마라. 다른 ID·미판독·범위 이탈·오래된 프레임·중복 프레임·시간 역행·프레임 공백의 처리를 명시하라. 첫 구현은 무효 관측에서 유지 상태를 리셋하는 명확한 정책을 사용하고, 예외를 허용하면 설정·테스트로 고정하라. 마지막 검출값만으로 시간이 지나 성공하는 현상을 방지하라. 성공/시간 초과 경계와 늦게 도착한 프레임의 처리도 결정적으로 정의하라.

필요 설정: 목표 표식, `center_tolerance_x`, `center_tolerance_y`, `area_ratio_min/max`, `hold_seconds`, `max_frame_age`, `max_frame_gap`, `time_limit`, 선택적인 중립 임계값. 범위·단위·유한값을 검증하라.

넓음/좁음은 우선 수평 중앙 허용범위만 다르게 한다. 실물 표식·면적 범위·수직 기준·유지 시간·카메라 설정 등은 동일하게 둔다. 이미지 프레이밍 난이도를 물리적 위치 허용오차라고 부르지 마라.

판독은 로봇 측 동일 카메라 경로에서 수행하라. 앱마다 수신된 JPEG로 개별 성공 판정을 하지 마라. 기존 원본 카메라 경로에서 분기하고, 같은 장치를 중복 오픈하거나 보행 제어 루프에서 판독·파일 쓰기를 실행하지 마라. 실제 설치 버전에 맞는 OpenCV 등의 라이브러리를 확인하라. 처리율·지연·프레임 누락을 로그에 남겨라.

### 5.2 실험 상태와 제어 연결

기본 상태는 `setup → ready → countdown → running → success / timeout / aborted`이다.

- 준비: 활성 제어 클라이언트, 중립 확인, 최신 카메라 프레임, 판독기 정상 동작, 로그 기록 가능 상태 확인. 목표 표식이 이미 읽혀야 준비되는 구조로 만들지 말 것.
- 시작: 참가자·trial·조건·난이도·설정 스냅샷 고정. 공통 신호 제공과 실제 클라이언트 신호 제시 사건 기록.
- 진행: 현재 trial과 제어 `client_id`를 연결하고 최초 입력·판독·프레이밍 진입/이탈·유지 리셋을 기록.
- 종료: 종료 결과를 한 번만 확정하고 중립·조작 차단 처리. 재전송된 시작/종료로 중복 trial이나 성공 사건이 생기지 않게 할 것.
- 다음 시행: 놓기·중립 ACK·새 조작을 거쳐 재개. 계속 잡거나 터치한 채 자동 재출발하지 않게 할 것.

실험 관리자와 이동 명령 채널의 책임을 구분하라. 실험 상태·trial ID는 별도 버전 있는 채널로 보내고, 엄격한 기존 v2 이동 패킷에 필드를 임의로 추가하지 마라. 일반 모드의 미디어 장애와 조종권 정책은 보존하되, 실험 모드에서 필요한 카메라/판정 채널 상실 시의 중단·중립 정책은 명시적으로 구현하라.

시작·종료 사건의 ID와 재시도 처리를 정의하고, 현재 trial과 관계없는 세션의 메시지를 거부하라. 자동 중립은 기존 비상정지 latch를 해제하는 동작이 아니다.

### 5.3 입력과 조종 시스템

현재 `PuppyPiV2Client.input`은 `BallGripInput`에 직접 연결되어 있다. 공통 코드가 정규화된 두 축, 조작 중 여부, 입력 유효성, 중립 요청을 받을 수 있도록 최소한의 입력 경계를 만들라.

- 스마트폰 (`smartphone_touch`): 터치 조이스틱에서 전후·회전 동시 입력, touch up/cancel·focus 상실 시 중립, 재접속·정지 절차 구현.
- MR (`mr_ballgrip`): 기존 BallGrip 유지. grab/release, 추적 상실, 차단 이유와 복구를 실험 로거에 연결.
- 공통: 같은 v2 정책·속도 상한·송신 주기·출력 필터를 사용하고 입력별 범위·감도·데드존을 기록.
- 두 장치의 원시 단위가 다르므로 감도 숫자를 억지로 같게 하지 마라. 파일럿에서 양쪽 모두 정상 사용 가능하게 조정한 뒤 설정을 고정하라.
- Unity 인터페이스 도입 시 기존 serialized 필드·장면·프리팹 호환을 고려하라. 기존 `.meta`와 GUID를 보존하고, 필요하면 호환 어댑터나 명시적 마이그레이션을 사용하라.
- 스마트폰이 웹이면 UDP로 이어지는 중계 구조·지연을 명시하라. 웹 경로와 Quest 경로가 같다고 가장하지 마라.

실험 모드에서는 속도·감도·콘솔 위치·카메라/지도 표시 정책을 설정 스냅샷에 넣고 임의 변경을 통제하라. 두 시스템의 피드백 정보와 시작/완료 알림을 맞추고, 필요한 연결·정지·중단 수단은 접근 가능하게 유지하라.

## 6. 로그 계약과 자료 산출물

원본 이벤트와 샘플은 버전 있는 JSONL 등으로 남기고 분석 CSV는 원본에서 생성하라. 로그 파일은 Git에 넣지 말고 기본 출력은 이미 무시되는 `.local/experiments/` 또는 별도의 명시적 출력 디렉터리로 둔다. 보고서는 `TestResults/`를 사용한다.

공통 레코드에는 적어도 다음이 있어야 한다. 이름은 일관된 대안으로 변경할 수 있으나 스키마와 예제를 제공하라.

```json
{
  "schema_version": 1,
  "event_id": "unique-record-id",
  "experiment_session_id": "session-id",
  "trial_id": "trial-id",
  "participant_id": "anonymous-id",
  "interface_id": "mr_ballgrip",
  "period_index": 2,
  "difficulty_id": "pilot-wide",
  "source": "robot",
  "clock_id": "identified-timebase",
  "t_mono_us": 123456789,
  "record_type": "event",
  "event_type": "framing_hold_started",
  "payload": {"frame_id": 42, "control_client_id": "client-id"}
}
```

위 JSON은 형식 예제이며 실제 참가자나 측정 결과가 아니다. 다음 데이터를 연결하라.

| 데이터 | 최소 기록 |
| --- | --- |
| 실행 manifest | `interface_id` 정의·실제 `interface_order`, 코드 버전, 앱·로봇 설정, 표식·배치·카메라 사양, 시계 정렬 정보, 설정 hash/version |
| 입력 | 원시·정규화 축, engagement, 추적/입력 유효성, focus/pause |
| 명령 | 실제 송신·로봇 수신·수락, client ID·sequence, 명령 값, ACK·거부·timeout |
| 상태 | 제어 가능 여부, 원인별 차단 시작/종료, 중립 확인·새 조작 필요·정지·복구 |
| 판독 | 원본 프레임 ID·시각, 판독 내용·모서리·중심 편차·면적, 처리 지연·누락 |
| 과제 | 신호 제시, 최초 입력·판독·프레이밍 진입/이탈, 유지 시작/리셋, 성공·시간 초과·중단 |
| 기록 품질 | 로깅 시작/종료·큐 초과·누락 수·부분 기록·파일 오류 |

다른 기기의 단조 시각을 직접 빼지 마라. 실제 클라이언트 시작 신호 제시 시각과 로봇 판정 시각을 연결할 시계 정렬·동기화 방법을 구현하고 오차를 저장하라. UTC는 사람을 위한 시간표시와 단조 시각의 간격 계산을 구별한다. 시계 정렬이 불충분한 시행은 잘못된 정밀 시간으로 출력하지 말고 품질 상태를 표시하라.

로깅은 bounded queue·버퍼·비동기 저장으로 조종을 막지 않게 하고 누락을 감추지 마라. 종료 시 기록을 정리하되 제어 스레드에서 무기한 기다리지 마라. 재시행도 원 시행을 삭제하지 않고 관계와 원인을 남겨라. 가능하면 사건 전후 로봇 카메라 프레임을 남겨 판정 재검토에 사용하라. 원본 영상 보관 범위와 누락도 설정·기록하라.

## 7. 운영 화면과 분석 도구

실험자 운영 화면 또는 동등한 간단한 CLI를 제공하라.

- 익명 참가자, `interface_id`, 난이도, 연습/본 시행 선택.
- 현재 제어 소유자·중립·카메라·판독·기록 준비 상태 확인.
- 시작·중단·다음 시행·자료 내보내기. 실패 이유와 원 시행 보존.
- 스마트폰→MR / MR→스마트폰 제시 순서와 난이도/목표 순서 관리. 배정 방법·실제 순서·seed를 기록.

분석 도구는 최소 다음 열의 trial 요약 CSV를 재생성해야 한다.

- 식별자·`interface_id`·`difficulty_id`·제시 순서·연습 여부·설정 버전.
- `outcome`: success / timeout / aborted와 원인.
- 신호→첫 유효 입력, 신호→성공, 첫 유효 판독→성공, 첫 프레이밍 진입→성공.
- 진입 후 재이탈, 공통 명령 기준 축별 방향 반전.
- 조종 요구 구간 중 시스템 이유로 차단된 시간과 재진입 시간. 중첩 차단을 이중 합산하지 말 것.
- 원본 프레임 갱신·판독 지연·누락·시계 정렬·로그 완전성의 품질 정보.

첫 판독을 물리적 접근 완료로 부르지 마라. 패킷 수·터치 이벤트 수·렌더 프레임 수를 조작 횟수로 직접 비교하지 마라. 방향 반전 계산의 공통 재표본화·데드존·히스테리시스·최소 유지시간을 설정과 분석 버전에 남겨라.

시간 초과의 완료 시간은 성공값으로 채우지 말고 종료까지 관측 시간과 성공 여부를 분리하라. 실패 시행을 삭제하여 성공한 시행만으로 주결과를 만들지 마라. 여러 trial이나 로그 행을 독립 참가자 수로 세지 마라. 초기 구현은 재현 가능한 자료·지표 추출에 집중하며, 유의한 차이를 자동으로 골라내는 기능을 만들지 마라. NASA-TLX·SUS는 처음부터 앱에 내장할 필요 없이 익명 ID로 외부 응답과 연결할 수 있게 하라.

## 8. 단계별 구현과 완료 기준

### 단계 1 — 판정 코어·fixture·모터 없는 재생

- 실제 카메라/ROS에 종속되지 않는 검출 결과 계약, 설정 검증, 유지 판정기 구현.
- 녹화·정적 프레임과 모의 검출을 넣는 재생 경로 제공. 모의 결과와 실제 QR 판독 검증을 구별.
- QR 영상에서 문자열·모서리 검출을 시도하고, 실제 로봇 접근이 가능할 때 원본 카메라에 연결.
- 같은 fixture와 설정에서 같은 사건이 재현되어야 한다.

### 단계 2 — 공통 trial·로그·운영 도구

- 상태기·시계/사건 연결·idempotency·공통 로그 구현.
- mock 실행으로 시작→입력→판독→성공과 시간 초과·중단 경로를 기록.
- 저장된 로그에서 요약 CSV와 성공 판정을 다시 생성할 수 있어야 한다.

### 단계 3 — 스마트폰·MR 입력·실험 모드 연결

- 기존 중립·ACK·재잡기 정책을 보존하면서 공통 입력 경계와 모의 입력 검증.
- Quest 실험 모드와 스마트폰 터치 입력 연결. 대상 OS가 없으면 Editor/플랫폼 독립 부분까지 완료하고 실제 빌드 항목만 남김.
- 기존 일반 조종과 실험 조종의 진입·종료 및 오류 처리를 확인.

### 단계 4 — 통합·파일럿 준비

- 가능한 환경에서 Unity·Python·프로토콜 회귀 검증.
- 실제 카메라를 사용할 수 있으면 조명·표식 크기·보행 진동·처리 부하·출발 즉시 판독 여부 확인.
- 1m 배치·프레이밍 2수준·시행시간을 확인하고 파일럿 설정과 미검증 항목을 명시.

장치 접근 부재는 오프라인 코어·mock·재생·분석 구현을 멈출 이유가 아니다. 반대로 mock 통과를 실제 Quest 손 추적, 폰 조종, Pi 보행 검증 완료로 보고하지 마라. 별도 로봇 소스에 접근할 수 없으면 현재 구현 가능한 공통 코드와 계약·fixture를 완성하고 필요한 로봇 어댑터의 미완료 범위를 명시하라.

## 10. 범위·운영 원칙

- UDP 제어 5001, discovery 5002, 현재 중립 ACK·새 잡기·watchdog·소유권·비상정지 의미를 보존한다.
- QR 판독·연구 로그를 위해 다른 클라이언트의 조종권을 강제로 빼앗거나 중립·정지 처리를 우회하지 않는다.
- 기존 사용자 장면·자산 변경을 보존하고 전체 장면 재구성 도구를 무심코 실행하지 않는다.
- 실제 로봇 IP·계정·체크아웃·ROS 경로를 추측하지 않는다. 코드 구현과 모터 없는 검증부터 수행하고, 실제 배포·서비스 재시작·주행은 확인된 사용자 요청과 장치 조건에 맞춰 별도로 다룬다.
- 초기 범위에 SLAM 개선, 외부 위치 계측, 자율 복귀, 자율주행, 장애물 코스, 시선 추정, 새 설문 플랫폼을 추가하지 않는다.
- 거대한 프레임워크나 두 가지 모바일 구현을 동시에 만들기보다 공통 계약과 하나의 사용 가능한 경로를 구현한다.

## 11. 최종 인계 결과

작업 종료 시 다음을 남겨라.

1. 변경 코드와 설정 예제, 실제 추가·변경 파일 설명.
2. 실험 채널·상태기·로그 스키마·시간 기준·판정 기준 문서.
3. 모터 없는 mock/replay 실행 방법과 로그→CSV 재생성 명령.
4. 테스트 결과·실행 명령·실행하지 못한 이유. Editor/mock/녹화/실기기 검증을 구분.
5. 스마트폰 대상·로봇 소스·카메라·파일럿 기준 중 남은 결정과 실제 장치에서 확인할 절차.

스킬 설치는 구현의 필수 선행조건이 아니다. 필요한 연구 설계 제약은 이 문서에 포함되어 있다. QR 라이브러리 API는 실제 설치 버전에 맞춰 [OpenCV QRCodeDetector](https://docs.opencv.org/4.13.0/de/dc3/classcv_1_1QRCodeDetector.html)와 [GraphicalCodeDetector](https://docs.opencv.org/4.13.0/d7/d90/classcv_1_1GraphicalCodeDetector.html)를 참고하라. 이 링크의 버전이 로봇에 설치된 버전이라는 뜻은 아니다.
