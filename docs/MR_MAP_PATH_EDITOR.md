# MR Map Path Editor

See [execution validation](MR_NAVIGATION_VALIDATION.md) for the full draw → RUN → bypass → completion scenarios, latest results and hardware limits.

The MAP tab's **OPEN MAP / DRAW PATH** button opens a separate world-space map window. Grab its outer rim to move it; use two hands to resize it uniformly. The camera window and cockpit stay independent.

## Operator-supervised navigation (default)

`PuppyPiPathClient.operatorSupervisedNavigation=true` is the default. The operator watches the robot and selects RUN; MR avoids confirmed current obstacles without requiring the entire route to have been measured free first. Unknown cells, missing rays, scan-filter startup and a starting point more than 0.30 m from the robot no longer reject an otherwise valid route. The route connects from the current robot position to the first unreached drawn point.

The displayed map retains its evidence: light blue-grey is still unknown, not measured free space. A separate padded planning grid treats those cells and the displayed crop's outer margin as traversable while retaining current confirmed obstacles. Accumulated obstacle debris is not imported. If an obstacle intersects the robot's current body, or no bypass can avoid a confirmed obstacle, execution remains unavailable or stopped.

Manual STOP/emergency stop, ownership, neutral ACK, a current robot position and valid map frame/session remain required. Communication watchdogs and lifecycle cancellation remain active. Robot-side pose/scan freshness rules are independent and are not overridden by this MR mode. Set `operatorSupervisedNavigation=false` to restore strict navigation, where unknown cells and scan freshness can block RUN and cancel execution.

## Draw and preview

1. Connect to the robot and wait for its map, position, and control ownership.
2. Open the map window and select **DRAW**.
3. Either touch the map with a finger and drag, or point at it from a distance and pinch-drag. Starting near the red robot marker makes the intended first leg easier to review; supervised mode also accepts a more distant starting point.
4. Release to straighten the route. Wavy input intended as one straight section becomes a single line between its endpoints. Distinct large turns create corners between fitted straight sections; diagonals are not forced onto horizontal/vertical axes. Endpoints stay fixed. `correctionToleranceMeters` controls noise discrimination rather than maximum ink deviation. The route is a thin line; dashed edges show its checked width, without a solid clearance band. Green means ready under the selected navigation policy, not proof that every cell was measured free; amber means unchecked, and a red cross identifies a confirmed occupied cell; an amber outline identifies unobserved cells or the map boundary. The status gives the cell coordinates and source. Dark cells are temporally confirmed current LiDAR obstacles. White cells are measured free space or eligible map-known-free cells; light blue-grey cells lack recorded free-space evidence. Unconfirmed sensor returns remain candidates rather than dark obstacles. Old accumulated obstacle points are neither displayed nor used to reject a route. `VERIFYING OBSTACLE` describes strict-preview or runtime persistence checking; `RUN BLOCKED` explains a control gate; `NO ROUTE` explains a failed bypass calculation.
5. Review the result, use **UNDO** or **CLEAR** if needed, then select **RUN**. Releasing a finger never starts movement.

Only one pointer may draw at a time. Window manipulation is disabled during a stroke. Leaving the image, losing the active pointer, changing the map coordinate frame/session, or hiding the window cancels the stroke. Short sensor/HTTP delays do not cancel drawing or close the map. The robot protocol supports up to 20 waypoints; ordinary input noise must not consume that budget. There is no 11-point limit.

## Run and stop

The same UDP session sends the robot's Protocol v2 `path` and `path_cancel` messages. Neutral commands continue at 20 Hz while the robot follows the route. The UI confirms execution through `/api/path`; a UDP acceptance alone is not displayed as running.

Automatic forward detours are enabled by default. A confirmed obstacle on the drawn route can preview a bypass before RUN without an additional route-confirmation warm-up. During execution, a persistent route conflict still uses three distinct observations spanning at least 0.40 s before requesting a bypass. A short sensor return, unknown cells or an unconfirmed robot `blocked` status retain the original route in supervised mode; they do not cancel it. Missing or old obstacle observations pause MR's bypass assessment while the requested route is retained. Confirmed occupancy in the robot's current body area cancels immediately. See [LiDAR noise filtering and verification](MR_LIDAR_NOISE_FILTER.md).

After confirming a persistent route obstacle, the MR client cancels the current route, waits for an accepted cancellation ACK and a subsequent fresh inactive HTTP snapshot, then waits for neutral ACK and plans from the current pose to the remaining original waypoints. It sends the replacement once after current control/coordinate checks. Movement remains forward straight sections separated by stopped turns; reverse is not used. The display follows remaining execution points rather than connecting back to a previous starting point. Supervised mode has no three-detour cap and may reuse the original route if the obstruction disappeared while stopping. Insufficient turning space around a confirmed obstacle, no alternative, or lost control/position still leaves the robot stopped. STOP, manual input and lifecycle/session changes revoke pending detours, including losses while cancellation is still in flight. Routes never restart after a connection loss. Eight seconds without meaningful target-directed movement (5 cm) or turning (0.05 rad), while navigation observations are available, cancels execution; these are project policies, not manufacturer guarantees.

Use **STOP** to cancel a route, or the existing emergency-stop control when needed. Grabbing the manual control, closing the map, app focus/pause changes, stale telemetry, and map identity changes cancel automatic movement. After interruption, review the route explicitly before another run. Manual control retains neutral acknowledgement and re-grab requirements.

## Data and robot requirements

- UDP 5001: the ROS 2 receiver with `path` enabled, using the new `PuppyPI_Cpp_ROS2` protocol extension.
- HTTP 8090: `/api/map` (session identity) and `/api/path` (execution state).
- Read-only ROS bridge on 9090: `/map` (`OccupancyGrid`), `/lidar_map/pose` (`PoseStamped`), and `/scan` (`LaserScan`), plus the read-only `/lidar_mapper/get_parameters` service. The service supplies the actual laser offset/yaw and map/base frames; the client never substitutes guessed calibration values.
- The map window displays confirmed current LiDAR endpoints, projected through an exact source-timestamp-matched pose into the grid's metre coordinates. Bounded sensor queues preserve frames while their matching pose arrives. Editing keeps the last coordinate-valid map and marker during short gaps. The default navigation freshness limit is 1.25 s; older data is never stamped as fresh. In supervised mode, missing scan/calibration data suspends obstacle assessment without independently rejecting RUN when the map identity and robot position remain usable. Strict mode requires verified navigation data for execution. Coordinates are not inferred from asynchronous MJPEG frames. The robot retains its independent sensor timeout/stop rules.
- The accumulated grid supplies coordinate geometry and the selected known-free prior. `MapKnownFreeLayer` fills only current unknown cells whose `BaseOccupancy` value is `0`–`25`, inclusive, matching the mapper's `free_thresh=0.25` classification of graded occupancy probabilities. Values `-1`, `26`–`49` and `50`–`100` never supply free permission. Confirmed current obstacles override the prior; accumulated occupied cells are not copied into the display or collision layer. A confirmed hit revokes prior permission at that world cell until a direct measured-free observation clears it, even if the source map still says `0`–`25`. Aligned crops and reconnect presentation resets retain that veto.
- The current laser layer starts unknown. Valid calibrated rays mark free space immediately, up to 10 cm or two cells before their endpoints. Small adjacent, continuous valid rays can fill fully observed cells between them; invalid rays, wide angular gaps and depth discontinuities are not bridged. Missing rays and unconfirmed candidates can reuse at most one second of measured-free evidence at its original scan/pose receipt time, or eligible map-known-free permission. These sources have separate provenance: map permission never receives a synthetic fresh observation time. Free evidence expires without a new scan; lifecycle/calibration/geometry changes reset the relevant evidence. Integer-cell viewport crops preserve overlapping evidence at its original age. Bounded confirmation history does not display absent endpoints as obstacles. These evidence rules still govern the display and strict navigation; supervised route admission does not require measured-free permission in every cell.
- The default body dimensions are **0.226 m long × 0.149 m wide**, from [Hiwonder's official PuppyPi specification](https://www.hiwonder.com.cn/product-detail/PuppyPi-2025.html). `robotFootprint.marginMeters=0.05` is an implementation allowance on each side for walking, not a manufacturer guarantee. Straight movement checks the swept oriented rectangle (default width 0.249 m); heading changes check the body's circumscribed turning radius. Detour planning also respects the deployed follower's frontal guard: 0.16–0.46 m ahead, at least ±0.17 m wide. Preview and planning use the same physical turning check. The 0.80 m preferred clearance is a soft route cost, not another hard turn-exclusion radius; a narrower verified passage remains usable.
- Detours use bounded heading-aware search, check every shortcut, and respect the existing 20-point protocol limit. Healthy requested corners are preserved; intermediate corners physically covered by blocked cells can be bypassed with explicit skipped-goal metadata. The final endpoint is never omitted. A soft clearance preference and turn costs favor broader, simpler routes without inflating every cell into a hard obstacle. See [open-source references and implementation scope](MR_AVOIDANCE_REFERENCES.md). Planning cannot compensate for inaccurate localization, a sensor plane missing a low obstacle, or physical walking drift. Robot-side ownership, emergency stop and independent scan/pose timeouts remain authoritative.

Validate drawing with both poke and ray on Quest, then use short straight and L-shaped routes on a clear floor before larger routes. This implementation does not detect table edges, stairs or loss of floor support: a clear horizontal LiDAR ray does not certify ground beneath the robot. Keep emergency stop latched for tabletop map inspection. For floor driving, release the grip and select **CLEAR STOP** to clear a VR stop, wait for neutral ACK, then review a new route and select **RUN**. For the reproduced forward blind-sector stall and selected known-free policy, see [forward-stall diagnosis](MR_FORWARD_STALL_DIAGNOSIS.md). Repository tests cover coordinate conversion, correction, pointer capture, window transforms, protocol correlation, and cancellation; they do not establish physical tracking accuracy.
