# VR–PuppyPi 2축 조종 및 제어 규격 v2 변경 요청

작성일: 2026-09-28  
상태: VR 측 설계 방향 및 로봇 측 구현 요청안 — 양측 확인 후 적용

## 1. 요청 요약

전달해주신 노트북 원격조종 문서와 `Puppy-PI-Cpp` 코드를 확인했습니다. VR에서는 **2축 그립으로 전후진과 회전을 동시에 조종**하는 방향으로 진행하려고 합니다.

통신은 기존 노트북 프로그램의 UDP·JSON·ACK 구조를 활용하되, 실제 속도인 `x`, `yaw_rate` 대신 **정규화한 조작 강도 `forward`, `turn`을 보내는 v2 규격**으로 변경하고 싶습니다.

- VR은 손잡기의 잡기 상태·기울기·감도를 처리합니다.
- 로봇은 조작 강도를 실제 속도로 변환하고 속도 상한·가감속·정지를 처리합니다.
- 그립을 놓으면 중립 명령을 보내며, 통신이 끊기면 로봇 측 watchdog으로 정지합니다.

이 문서는 기존 `VR_PuppyPi_통신규격_협의안.md`의 초기 제안보다 우선하는 **최신 전달안**입니다. 아직 양측 프로그램에 구현된 규격이라는 뜻은 아닙니다.

검토 기준 저장소: [Ksyear/Puppy-PI-Cpp](https://github.com/Ksyear/Puppy-PI-Cpp)  
검토 커밋: `95ada75e06d65c48c5b51eaeb7a18be884c54b8e`

## 2. VR 조작 방식

| 조작 | 이동 명령 |
|---|---|
| 앞으로 기울임 | 전진 |
| 뒤로 기울임 | 후진 |
| 왼쪽으로 기울임 | 좌회전 |
| 오른쪽으로 기울임 | 우회전 |
| 대각선으로 기울임 | 전후진과 회전을 동시에 적용하는 곡선 이동 |
| 기울기를 크게 함 | 해당 명령 강도 증가 |
| 현재 조종 중인 그립을 놓음 | 중립 전환, 정지 요청 |

현재 로봇 경로의 `y`는 0으로 유지합니다. 대각선 조작은 옆으로 평행 이동하는 동작이 아닙니다. 몸체 roll·pitch·높이 제어는 이번 이동 규격에 포함하지 않습니다.

VR은 BallGrip과 StickGrip 중 현재 선택된 그립 하나의 입력만 사용합니다. 그립별 전략은 공통된 `forward/turn`을 출력하고, 송신기는 하나만 둡니다. 그립 종류는 로봇에 전송하지 않습니다.

그립 감도는 중앙에 중립 구간을 두고, 작은 기울기에서는 미세 조종하고 큰 기울기에서는 속도를 높이는 방향입니다. 저속·중속·고속 버튼처럼 고정값만 보내기보다 연속적인 값을 보내려고 합니다. 실제 보행 엔진에서 단계화가 필요하다면 로봇 측 처리 방식과 최소 유효 속도를 공유 부탁드립니다.

## 3. 역할 분담

| VR 측 | 로봇 측 |
|---|---|
| 잡기·놓기와 추적 상태 감지 | 메시지 형식·범위·순서·조종자 검증 |
| 현재 그립 전략 선택 | 정규화 입력을 실제 속도로 변환 |
| 관절 축 보정, 중립 구간, 감도 곡선 | 전진·후진·회전 속도 상한 관리 |
| `forward/turn` 생성 및 주기 송신 | 보행 안정성을 위한 가감속·동시 입력 제한 |
| 입력 상실 시 즉시 중립 송신 | 중립·비상정지·통신 단절 시 정지 |
| ACK 감시 및 재연결 시 재조작 요구 | ACK 응답 및 조종 세션 관리 |

VR과 로봇 양쪽에서 관절 각도 변환이나 같은 감도 곡선을 중복 적용하지 않습니다. 로봇은 Unity의 X/Z 회전각을 알 필요가 없습니다.

## 4. 기존 노트북 규격에서의 변경점

| 항목 | 기존 v1 | 제안 v2 |
|---|---|---|
| 프로토콜 구분 | `protocol: 1` | `protocol: 2` |
| 이동 필드 | `x`, `yaw_rate` | `forward`, `turn`, `control_active` |
| 이동 값 의미 | cm/s, rad/s 단위 실제 목표 속도 | 각각 -1~1의 조작 강도 |
| 일반 정지 | 속도 0 | `control_active: false` 및 두 축 0 |
| 시간 필드 | 송신 `timestamp` 기반 나이 검사 | 기본 메시지에서 제거. 수신 측 경과시간으로 watchdog 처리 |
| 유지할 구조 | UDP, JSON, UUID, sequence, ACK, 단일 조종자, 비상정지 | 기존 구조를 활용하되 v2 상태 규칙에 맞게 조정 |

포트는 **UDP 5001**, 전송 주기는 **20Hz**를 유지하는 것으로 제안합니다. UTF-8 JSON 객체 하나를 UDP 데이터그램 하나로 전송합니다. ACK는 그 패킷을 보낸 UDP 주소로 회신합니다.

기존 v1과 자동으로 섞어 해석하지 않고 `protocol`로 명확하게 구분해주세요. v1 노트북 프로그램도 유지한다면 파서를 분리하되, 최종 이동 명령의 소유권과 정지 상태는 공유해야 합니다. 기존 VR 5005 수신기 등 다른 프로그램이 같은 이동 토픽에 동시에 명령을 발행하지 않도록 실행 구성을 정해야 합니다.

## 5. v2 명령 메시지

```json
{
  "protocol": 2,
  "type": "command",
  "client_id": "d8b27f10-09a8-4c21-b649-1e7058d46b72",
  "sequence": 123,
  "control_active": true,
  "forward": 0.6,
  "turn": -0.3
}
```

| 필드 | 자료형·범위 | 의미 |
|---|---|---|
| `protocol` | 정수 `2` | 새 규격 버전 |
| `type` | 문자열 | 아래 메시지 종류 중 하나 |
| `client_id` | 표준 UUID 문자열 | 앱 실행마다 새로 생성. 같은 실행 동안 유지 |
| `sequence` | 정수 0~9007199254740991 | 세션 내 메시지마다 증가. 중립·이벤트도 같은 번호 흐름 사용 |
| `control_active` | 불리언 | 현재 유효한 그립 조종 입력이 있는지 |
| `forward` | 유한한 숫자 -1~1 | 양수 전진, 음수 후진 |
| `turn` | 유한한 숫자 -1~1 | 양수 좌회전, 음수 우회전 |

방향은 로봇이 바라보는 전방 기준입니다. 후진 중에도 `turn`의 좌회전·우회전 부호는 유지합니다. `turn`은 자동차의 조향각이 아닌 로봇의 회전 속도에 대한 강도입니다.

모든 명령 필드는 필수입니다. 숫자는 문자열이나 불리언으로 받지 않고, `NaN`·무한대·범위 초과는 거부해주세요. 정상 메시지를 실제 속도로 변환한 뒤에도 로봇 측 최종 속도 제한은 유지합니다. 알 수 없는 필드는 기존 파서처럼 거부하는 것으로 제안합니다.

## 6. 실제 속도 변환

로봇 측 설정값을 기준으로 변환해주세요.

```text
forward >= 0: x = forward × 최대 전진 속도
forward <  0: x = forward × 최대 후진 속도의 크기
y = 0
yaw_rate = turn × 최대 회전 속도
```

현재 노트북 서버의 기본 제한값을 유지하면 다음과 같습니다.

| 설정 | 초기값 |
|---|---|
| 최대 전진 속도 | 5cm/s |
| 최대 후진 속도의 크기 | 3cm/s |
| 최대 회전 속도 | 0.20rad/s |

예를 들어 `forward=0.6, turn=-0.3`은 제한·가감속 적용 전 `x=3cm/s, yaw_rate=-0.06rad/s`가 됩니다. `forward=-0.5`는 `x=-1.5cm/s`입니다.

이 값들은 초기 시험 설정이며 로봇의 물리적 최대 성능을 뜻하지 않습니다. 전후진과 회전을 동시에 최대로 요청했을 때의 안정적인 제한, 가감속 속도, 저속 출발 조건은 로봇 측에서 정하고 공유 부탁드립니다. VR에서는 실제 다리의 보행 위상이나 서보 각도를 직접 지정하지 않습니다.

## 7. 중립과 정지

```json
{
  "protocol": 2,
  "type": "command",
  "client_id": "d8b27f10-09a8-4c21-b649-1e7058d46b72",
  "sequence": 124,
  "control_active": false,
  "forward": 0.0,
  "turn": 0.0
}
```

- `control_active: true`이고 두 축이 0이면 손잡기를 잡고 중립에 있는 상태입니다. 이동 목표는 0입니다.
- 유효한 메시지가 `control_active: false`이면 두 축의 값보다 우선하여 이동 목표를 0으로 처리해주세요. VR은 두 축도 항상 0으로 보냅니다.
- VR 시작, 그립 놓기, 추적 상실, 앱 일시정지·포커스 상실 시 중립으로 전환합니다. 전환 시에는 다음 50ms 주기를 기다리지 않고 즉시 전송합니다.
- 송신 루프가 살아 있는 동안에는 중립 명령도 20Hz로 계속 보냅니다.
- 앱 중단이나 통신 단절로 정지 패킷이 도착하지 않는 경우는 로봇 watchdog이 처리합니다.
- 정지 요청은 보행·회전 목표를 0으로 하는 것이며, 모터 전원 차단을 의미하지 않습니다. 정지 시 자세 유지와 감속 방식은 로봇 제어기에 맞춰 처리해주세요.

## 8. 메시지 종류와 비상정지

공통 필드는 `protocol`, `type`, `client_id`, `sequence`입니다.

| `type` | 추가 필드 | 요청 동작 |
|---|---|---|
| `command` | `control_active`, `forward`, `turn` | 이동 또는 일반 중립 |
| `emergency_stop` | 없음 | 이동을 정지하고 비상정지 상태 유지 |
| `clear_emergency` | 없음 | 비상정지 해제 후 중립 상태에서 새 조작 대기 |
| `disconnect` | 없음 | 정지 후 현재 조종자 소유권 해제 |

```json
{
  "protocol": 2,
  "type": "emergency_stop",
  "client_id": "d8b27f10-09a8-4c21-b649-1e7058d46b72",
  "sequence": 125
}
```

그립 놓기는 일반 중립이며 비상정지를 걸지 않습니다. 비상정지는 별도 명시적인 사용자 동작으로 요청하고, 명시적으로 해제하기 전에는 이동 명령을 적용하지 않습니다. ACK에서 메시지 수신과 실제 이동 적용 여부를 구분할 수 있어야 합니다.

## 9. watchdog·재연결·조종자 관리

- 시작 시에는 이동 목표 0, 중립 확인 대기 상태로 둡니다.
- **마지막으로 인정한 새 유효 command 이후 250ms** 동안 command가 없으면 정지 처리를 시작해주세요. 기존 0.25초 값을 초기값으로 유지합니다. 실제 정지 완료 지연은 별도 측정합니다.
- 시간은 로봇 내부 단조 증가 시계로 측정합니다. 오류·중복·역순 패킷과 기타 메시지는 이동 watchdog을 갱신하지 않습니다. 정상 중립 command는 갱신합니다.
- UUID와 송신 주소 기반의 단일 조종자 구조를 유지합니다. 같은 세션의 sequence는 계속 증가하며 이전 번호 이하를 적용하지 않습니다.
- watchdog 정지·재연결·비상정지 해제 후에는 활성 명령만 받아 바로 재출발하지 않고, 새 중립 명령을 먼저 인정한 뒤 활성 명령을 허용해주세요.
- VR도 ACK 상실 시 중립으로 전환하고 기존 잡기 상태를 해제합니다. ACK가 복구되어도 자동 출발하지 않으며 사용자가 다시 잡아야 합니다. ACK 상실 판정 시간은 양측 통합 시험 전에 확정합니다.
- 새 앱 실행의 UUID로 소유권을 바꿀 때는 기존 조종자가 해제되거나 lease가 만료되어 정지된 상태여야 합니다. 기존 1초 lease를 초기값으로 활용할 수 있습니다.

### 시간 동기화와 지연 패킷: 추가 협의 필요

기존 송신 timestamp 검사에는 기기 간 시계 차이로 정상 명령이 거부될 수 있는 문제가 있어, v2 기본 패킷에서는 wall-clock timestamp를 제거하고 싶습니다.

다만 **sequence와 수신 watchdog만으로는 오래 지연됐지만 번호는 증가하는 패킷을 모두 걸러낼 수 없습니다.** 실제 제어 적용 전, 연결 시 시계 차이를 추정하는 방식이나 로봇이 발급하는 짧은 유효기간의 토큰 등으로 명령의 신선도를 보장할 방법을 함께 확정해야 합니다. 선택에 따라 v2 필드가 추가될 수 있으므로 이 부분은 구현 전 합의 항목입니다.

현재 세션을 교체한 뒤 예전 세션의 지연 패킷으로 소유권이 되돌아가지 않도록 하는 정책도 함께 확인 부탁드립니다.

## 10. ACK 제안

기존 ACK 응답 구조에 `client_id`와 수신기 상태를 추가하면 VR의 연결·재조작 안내에 사용할 수 있습니다.

```json
{
  "protocol": 2,
  "type": "ack",
  "client_id": "d8b27f10-09a8-4c21-b649-1e7058d46b72",
  "sequence": 124,
  "accepted": true,
  "reason": "ok",
  "emergency_stop": false,
  "state": "idle"
}
```

- `sequence`는 확인한 요청 번호를 그대로 회신합니다. 요청을 해석할 수 없어 번호를 알 수 없으면 기존처럼 `-1`을 사용할 수 있습니다. UUID를 알 수 없으면 `client_id`는 `null`로 제안합니다.
- `accepted`는 해당 요청을 프로토콜·상태 규칙에 따라 받아들였는지 뜻합니다. 실제 보행 성공이나 측정 속도 달성을 뜻하지 않습니다.
- `state` 후보는 `idle`, `active`, `timeout`, `emergency_stop`, `awaiting_neutral`, `fault`입니다. 이는 제어기 상태이며 실제 이동 감지값이 아닙니다.
- 비상정지 중 활성 command나 중립 확인 전 활성 command는 `accepted: false`로 응답하고 이유를 알려주세요. 중립 command와 정지 이벤트는 해당 상태에서도 처리할 수 있어야 합니다.
- `reason`은 `ok`, `invalid_packet`, `unsupported_protocol`, `out_of_order`, `not_owner`, `emergency_stop`, `neutral_required` 같은 고정 코드로 제안합니다. 표시 문장은 VR에서 처리합니다.
- VR은 현재 UUID와 보낸 번호에 대응하는 새 ACK만 연결 상태 판단에 사용합니다. 과거 ACK를 반복 수신했다고 연결이 정상인 것으로 판단하지 않습니다.

## 11. 영상 연결과 통합 시 주의할 부분

영상 자체의 포맷 변경은 이번 이동 규격 요청에 포함하지 않습니다. 기존 TCP 5000의 헤더+JPEG 방식은 별도 연동할 수 있습니다.

현재 서버는 영상 클라이언트가 있으면 같은 IP에서 온 제어 명령만 허용합니다. 영상은 노트북, 조종은 Quest로 나누면 거부될 수 있으므로 최종 장치 구성을 확인해야 합니다. 영상이 끊겼을 때 조종도 차단할지는 노트북 코드의 동작을 참고하여 VR과 서버에서 같은 정책으로 정하겠습니다.

노트북 프로그램에만 있는 포커스·ACK·영상 연결 차단 로직이 Unity에 자동으로 적용되지는 않으므로, 필요한 차단 조건은 양측에서 명시적으로 구현해야 합니다.

## 12. 수정 대상과 확인 요청

로봇 측에서는 아래 부분을 중심으로 검토 부탁드립니다.

- `puppypi_remote_camera/robot/remote_control.py`: v2 파서, 정규화 입력 변환, 중립·재연결 상태 규칙, ACK 변경.
- `puppypi_remote_camera/config/robot_config.yaml`: 버전, 속도 상한, watchdog·lease 설정. 가감속 및 복합 입력 제한의 적용 계층 결정.
- `robot_server.py`와 실제 보행 제어기: 기존 Velocity 발행을 활용하고, 정지·속도 변환 결과가 실제 엔진에서 어떻게 반영되는지 확인.
- 기존 노트북 클라이언트: v1을 계속 유지할지, v2로 함께 전환할지 결정.

다음 사항을 회신해주시면 VR 구현 기준을 맞출 수 있습니다.

1. JSON 5001 경로를 기준으로 위 v2 구조를 적용할 수 있는지.
2. 실제 장치가 사용할 ROS/보행 엔진과, 낮은 속도·전후진+회전 동시 명령의 시험 결과.
3. 초기 속도 상한 5cm/s, 후진 3cm/s, 회전 0.20rad/s와 20Hz·250ms watchdog의 적절성.
4. 가감속, 정지 지연, 최소 출발 속도와 필요한 단계화 정책.
5. timestamp를 대체할 지연 패킷 검증 방식과 ACK 상실 판정 시간.
6. 영상과 조종을 Quest가 함께 담당할지, 노트북과 나눌지 및 영상 단절 시 정지 정책.

## 13. 공동 확인 항목

| 시험 | 기대 결과 |
|---|---|
| 시작 후 손잡기를 잡지 않음 | 중립 유지 |
| 작은 기울기에서 큰 기울기로 변경 | 강도에 맞는 속도 변화, 설정 상한 준수 |
| 두 축 동시 입력 | 전후진하면서 회전 |
| 미선택 그립 조작 | 최종 송신 명령에 영향 없음 |
| 선택 그립 놓기·추적 상실 | 즉시 중립 요청, 관절 복귀 중 명령 발생 없음 |
| 통신 단절·오류 패킷 지속 | 유효 command 기준 watchdog 정지 |
| 중복·역순·다른 조종자 패킷 | 이동 적용 및 watchdog 갱신 안 됨 |
| 재연결·비상정지 해제 | 중립 확인과 새 조작 없이 자동 이동하지 않음 |
| 지연 패킷·이전 세션 패킷 | 합의한 신선도·세션 정책으로 거부 |
| 모터 비활성 시험 모드 | 실제 모터 동작 없이 변환값·ACK·정지 상태 확인 |

첫 통합은 모터 비활성 상태에서 메시지와 변환값을 맞추고, 이후 낮은 속도 설정으로 실제 보행 응답을 확인하는 순서로 진행하고 싶습니다.
