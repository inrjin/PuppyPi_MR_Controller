# 로봇 측 구조 분석 및 그립 축 설계

검토일: 2026-09-28  
저장소: https://github.com/Ksyear/Puppy-PI-Cpp  
검토 커밋: `95ada75e06d65c48c5b51eaeb7a18be884c54b8e`

## 결론

한 번에 선택한 그립 하나로 전후진과 회전을 모두 조종하려면 **2축 그립**이 적합하다. 앞뒤 기울기를 전후진 속도, 좌우 기울기를 회전 속도로 매핑한다. 대각선 입력은 옆으로 걷기가 아니라 전진·후진과 회전을 합친 곡선 이동을 의미한다.

현재 이동 명령 경로는 전후진 `x`와 회전 `yaw_rate`라는 두 독립 값을 받는다. 로봇의 측면 이동 `y`는 0으로 고정된다. Unity의 회전 X축과 로봇의 전진 x는 서로 다른 좌표·물리량이므로 이름만 보고 연결하면 안 된다.

## 검토 범위와 한계

- 담당자가 전달한 `노트북_원격조종_정리.md`를 읽었다.
- 저장소 전체 구성과 루트 README를 확인하고, 노트북 원격조종, 기존 VR 수신 경로, ROS 제어 노드, 엔진 연결부 및 영상 경로를 중심으로 추적했다.
- ROS나 실제 로봇은 실행하지 않았다. 순수 Python 수신 로직을 가짜 출력 함수에 연결해 검증했다.
- 실제 Noetic 장치에 설치된 제조사 보행 엔진과 설정은 공개 저장소만으로 확인할 수 없다. ROS2 제어 코드의 동작을 현재 Noetic 장치의 동작으로 단정하지 않는다.
- SLAM·장애물 넘기기·자율주행 등 다른 패키지 전체에 대한 상세 품질 검토는 이번 범위가 아니다.

## 두 종류의 통신 경로

| 항목 | 전달 문서의 노트북 경로 | 저장소의 기존 VR 경로 |
|---|---|---|
| 중심 코드 | `puppypi_remote_camera/` | `src/puppy_vr_control/`, `_py`, `noetic_fallback/` |
| 제어 | UDP 5001, JSON | UDP 5005, `X:각도,Z:각도` |
| 입력 의미 | 실제 목표 속도 `x`, `yaw_rate` | 관절 각도를 수신 후 목표 속도로 변환 |
| ROS 환경 | ROS1 Noetic (`rospy`) | ROS2 구현 및 ROS1 대체 구현 |
| 영상 | TCP 5000, 30바이트 헤더 + JPEG | UDP 5006, JPEG 청크 |
| 정지 제한 기본값 | 명령 미수신 0.25초 | 명령 미수신 1초 |
| 제어 응답 | JSON ACK | 같은 ACK 규격이 아님 |

두 프로토콜은 서로 바꿔 쓸 수 없다. 루트 README는 주로 기존 VR/ROS2 경로를 설명하지만, 전달받은 문서는 별도 Noetic 노트북 프로그램을 설명한다.

## 노트북 경로에서 실제 이동 명령까지

```text
노트북 W/S, A/D 입력
  → x와 yaw_rate를 각각 계산 (W+A 등 동시 입력 가능)
  → UDP JSON 송신
  → 패킷·시간·송신자·순서 검증
  → x/yaw_rate 속도 제한, y=0 고정
  → ROS Velocity 메시지 발행
  → /puppy_control/velocity/autogait
  → 장치에 설치된 보행 제어기와 제조사 엔진
```

노트북 UI가 키보드이기 때문에 기본적으로 고정 속도를 보낼 뿐, 수신기는 실수 중간값도 받는다. 기본 설정은 전진 최대 5cm/s, 후진 최대 3cm/s, 회전 최대 0.20rad/s(약 11.5도/s)다. 이는 원격 프로그램의 설정상 제한이며 로봇의 물리적 최대 성능을 뜻하지 않는다.

`enable_motor_control: false`가 기본값이다. 이 상태에서는 실제 이동 토픽 대신 `/puppypi_remote_camera/test_velocity`로 발행한다. ACK가 성공해도 실제 모터가 움직였거나 목표 속도를 달성했다는 뜻은 아니다.

근거: [노트북 입력](https://github.com/Ksyear/Puppy-PI-Cpp/blob/95ada75e06d65c48c5b51eaeb7a18be884c54b8e/puppypi_remote_camera/laptop/laptop_client.py), [수신·제한·watchdog](https://github.com/Ksyear/Puppy-PI-Cpp/blob/95ada75e06d65c48c5b51eaeb7a18be884c54b8e/puppypi_remote_camera/robot/remote_control.py), [ROS 발행](https://github.com/Ksyear/Puppy-PI-Cpp/blob/95ada75e06d65c48c5b51eaeb7a18be884c54b8e/puppypi_remote_camera/robot/robot_server.py).

## 보행 제어기의 해석

공개 ROS2 Python 제어기의 `VelocityAutogaitFun`과 C++ 대응 코드는 다음 구조다.

1. 전후진·측면·회전이 모두 0이면 정지 함수를 호출하고 서기 자세를 적용한다.
2. 일반 이동은 `|x| <= 35`, `y == 0`, `|yaw_rate| <= 51도/s` 조건에서 처리한다.
3. 전후진 속도와 회전 속도 크기에 따라 발을 지지하고 움직이는 시간 등 보행 파라미터를 계산한다.
4. 전진 여부에 따라 자세 중심을 보정한다.
5. `move(x, y, yaw_rate)`로 엔진에 전달한다.

따라서 상위 입력은 전진/회전 동작 파일 선택이 아니라 속도 목표다. 다만 보행 파라미터 계산은 구간별 수식이므로 작은 입력 차이가 실제 보행에서도 완전히 매끄럽다고 보장할 수는 없다. 실제 저속 동작, 속도 전환과 복합 회전은 실기기에서 확인해야 한다.

몸체 roll·pitch·높이 조절은 별도 `pose` 경로에 있지만 노트북 조종 JSON에는 포함되지 않는다. 첫 이동 그립에 3축 회전·몸체 자세까지 섞기보다는 필요할 때 별도 자세 모드로 다루는 편이 명확하다.

Python 제어기는 저장소 밖의 `/home/ubuntu/software/puppypi_control` 엔진을 불러온다. 공개 C++ 엔진은 `stub_engine.cpp`이며 서보 출력이 없다. 로봇 측 비공개 구현이 없으면 공개 C++ 코드만 빌드해서 실제 보행을 확인할 수 없다.

근거: [Python 보행 제어기](https://github.com/Ksyear/Puppy-PI-Cpp/blob/95ada75e06d65c48c5b51eaeb7a18be884c54b8e/src/driver/puppy_control/puppy_control/puppy.py), [C++ 제어기](https://github.com/Ksyear/Puppy-PI-Cpp/blob/95ada75e06d65c48c5b51eaeb7a18be884c54b8e/src/driver/puppy_control_cpp/src/puppy_control_node.cpp), [공개 엔진 스텁](https://github.com/Ksyear/Puppy-PI-Cpp/blob/95ada75e06d65c48c5b51eaeb7a18be884c54b8e/src/driver/puppy_control_cpp/src/stub_engine.cpp).

## 그립 설계 선택지

| 설계 | 가능한 조종 | 기존 전략 선택 구조와 관계 |
|---|---|---|
| 1축 그립 하나 | 전후진 또는 회전 중 한 성분. 별도 입력 없이는 두 성분을 독립 조작 불가 | 단순 시험용으로 적합 |
| 2축 그립 하나 | 전후진, 제자리 회전, 전후진하며 회전 | 선택한 그립 하나가 완전한 이동 명령 생성. 권장 |
| 1축 그립 두 개 | 한쪽 전후진, 다른 쪽 회전 | 두 값을 합치는 복합 전략이 필요. 마지막으로 잡은 그립 하나만 선택하면 동시 조종 불가 |
| 3축 이상 그립 | 이동 외 추가 기능 필요 | 현재 이동 프로토콜에 대응하는 세 번째 독립 이동 성분 없음 |

BallGrip과 StickGrip을 서로 대체 가능한 조종 방식으로 만들 목적이라면, 각각 동일한 두 성분을 출력하게 하고 중립 전략·송신기 하나를 공통 사용한다.

현재 Unity 씬의 손잡이는 X축 HingeJoint로 제한돼 있다. 2축 입력은 송신 코드만 고쳐서는 만들 수 없다. 관절 구성, 회전 기준, 각도 제한과 중립 복귀도 함께 변경해야 한다. 구체적 관절 구현은 VR 잡기·물리 동작을 시험하며 결정한다.

## 우리 송신 규격에 미치는 영향

이전에 작성한 `VR_PuppyPi_통신규격_협의안.md`는 제안 상태로 보존한다. 현재 서버가 그 규격을 구현했다고 가정하면 안 된다.

노트북 서버를 그대로 사용할 경우 메시지는 아래 필드만 허용한다.

```json
{
  "protocol": 1,
  "type": "command",
  "client_id": "d8b27f10-09a8-4c21-b649-1e7058d46b72",
  "sequence": 123,
  "timestamp": 1753350000.12,
  "x": 2.5,
  "yaw_rate": 0.1
}
```

위 timestamp는 형식 예시일 뿐이며 실제 송신 시 현재 Unix 시간을 넣어야 한다. 현재 서버는 과거 0.3초 초과, 미래 1초 초과 패킷을 거부하므로 시계 동기화가 필요하다. 제안 문서의 `control_active`, `forward`, `turn` 등을 추가하면 현 파서는 거부한다.

호환 어댑터를 사용할 경우 VR 내부는 `forward/turn` 정규화 값을 유지하고 전송 직전에 변환할 수 있다. 현재 제한값 기준으로 양의 forward는 ×5cm/s, 음의 forward는 ×3cm/s, turn은 ×0.20rad/s다. 이 상한은 양측 설정과 일치시켜야 한다. 중립 전략은 `type: command, x: 0, yaw_rate: 0`으로 보낸다. 손을 놓는 일반 정지마다 수동 해제가 필요한 `emergency_stop`을 사용할 필요는 없다.

ACK는 송신 UDP 주소로 돌아오므로 같은 소켓으로 수신해야 한다. 서버는 UUID뿐 아니라 송신 IP와 UDP 포트도 소유권 판단에 사용한다. 영상 클라이언트가 있으면 그 IP와 제어 클라이언트 IP도 같아야 한다. 노트북이 영상을 받고 Quest가 제어하는 분리 구성은 현 서버에서 거부될 수 있다.

영상 단절 시 조종 차단은 노트북 클라이언트에도 구현되어 있다. 서버는 영상 종료 때 정지하지만 영상이 없는 상태의 새 유효 이동 명령을 무조건 차단하지는 않는다. Unity로 클라이언트를 교체할 때 영상 상태에 따른 조종 정책도 명시적으로 옮겨야 한다.

기존 VR 5005 경로를 유지하면 각도 정규화와 속도 단계화가 로봇 쪽에 이미 존재한다. 기본값은 1cm/s와 2도/s 단위 반올림이며 회전 부호 반전도 켜져 있다. VR과 로봇 양쪽에서 감도 변환·반전을 중복 적용하지 않도록 한쪽에 책임을 모아야 한다.

## 코드 수준 시험 결과

실제 소켓·ROS·모터를 사용하지 않고 `RemoteControlServer`에 메시지를 주입하고 발행값을 기록했다.

| 입력 | 발행된 (x, y, yaw_rate) |
|---|---|
| x=2.5, yaw_rate=0.1 | (2.5, 0, 0.1) |
| x=-1.5, yaw_rate=-0.07 | (-1.5, 0, -0.07) |
| x=99, yaw_rate=99 | (5, 0, 0.2), 설정 상한 적용 |
| x=0, yaw_rate=0 | (0, 0, 0) |
| 마지막 명령 후 0.26초로 시간 모의 | (0, 0, 0), watchdog 정지 |
| command에 y 필드 추가 | 패킷 거부 |

## 담당자에게 확인할 핵심 사항

1. 실제 로봇에서 사용할 경로는 Noetic JSON 5001인가, 기존 VR 각도 5005인가?
2. 장치에 설치된 실제 보행 엔진에서 작은 전후진 값과 전후진+회전을 시험했는가? 출발 가능한 최소 속도와 안정적인 동시 입력 범위는?
3. 입력이 계속 변할 때 보행 재설정으로 떨림이 생기는가? 단계화·가감속 제한은 어느 계층에서 담당할 것인가?
4. 최종 구성에서 영상과 조종을 모두 Quest가 담당하는가, 노트북과 나누는가?
5. VR 내부는 정규화한 이동 명령으로 유지하고 기존 JSON에 변환해서 보낼지, 서버를 새 협의안으로 변경할지?
