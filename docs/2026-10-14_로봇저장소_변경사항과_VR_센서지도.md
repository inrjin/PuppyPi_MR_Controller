## 1. 결론

센서 결과를 VR 콕핏에서 실시간으로 볼 수 있다. **사용자가 추가로 제공한 실제 결과 스크린샷은 복도·벽·천장이 색상 있는 점들로 표현된 3D 포인트클라우드로 보인다. 따라서 실제 목표는 이 3D 점군의 원본을 받아 Unity에서 입체 지도로 표시하는 것으로 정정한다.** 아래 2D 지도 분석은 저장소에서 확인한 별도의 경로에 해당하며 사용자의 실제 결과 전체를 설명하지 않는다.

스크린샷만으로 센서 모델, 생성 프로그램, 좌표 정확도, 실제 실시간 갱신 여부를 특정할 수는 없다. 사용자는 프로그램·센서 정보를 아직 모르며 담당자에게 확인이 필요하다고 답했다. 영상에 보이는 초록색 표시는 카메라 위치·방향을 나타내는 마커로 추정되지만 확정하지 않는다.

- 저장소의 2D 지도 이미지를 콕핏 화면에 표시: 기존 UDP 5008 송신 경로 활용 가능. Unity 수신·이미지 표시 구현 필요. 사용자가 제공한 3D 스크린샷의 원본 전송 경로라는 뜻은 아니다.
- 2D 지도 격자를 바닥과 장애물 기둥/벽으로 표시하고 로봇 위치·방향을 함께 표시: 지도 원본 데이터와 위치 전송을 추가하면 가능한 대안이다.
- 주변 사물의 높이·입체 형상 표시: 스크린샷을 생성한 기존 3D 재구성 경로에서 점군 원본을 받을 수 있다면 이를 재사용한다. 현재 확인한 2D 라이다 경로만으로는 불충분하지만, 사용자의 실제 장비에 3D 측정 기능이 없다고 단정하지 않는다.

장애물 격자를 일정 높이로 세우는 표현은 시각화용 높이다. 측정한 벽 높이나 실제 3D 형상으로 취급하지 않아야 한다. 빈 격자도 센서 스캔 높이에서 관측한 빈 공간이며, 물체의 위·아래나 낭떠러지까지 안전하다는 뜻은 아니다.

## 2. 지난 검토 이후 변경

비교 구간에는 구현 커밋 `c56463a`와 이를 합친 PR #1 merge 커밋이 있다. 20개 파일이 변경됐다. 라이다 지도 생성·지도 송신·기존 대시보드 코드는 이 구간에서 변경되지 않았다.

새 변경의 중심은 `puppypi_remote_camera/`의 Quest v2 제어다.

## 3. 찾은 센서·시각화 코드

### ROS1 Noetic 지도 경로

`noetic_fallback/puppy_vr_control_noetic/scripts/lidar_mapping.py`

```text
라이다 드라이버 → LaserScan
  → 거리·각도를 평면 점(x,y)으로 변환
  → 스캔매칭으로 로봇 위치(x,y,theta) 추정
  → 점유격자 생성
      ├ /map: OccupancyGrid 원본
      └ 로봇 중심 지도 이미지 → JPEG → UDP 5008
```

- 기본 지도는 12m × 12m, 셀 크기 0.05m: 240 × 240 격자다.
- 지도 송신 기본 주기는 1초다. 센서 스캔 처리 빈도, 지도 갱신 빈도, VR 렌더링 빈도는 서로 다르다.
- `render_bgr()`는 기본 약 6m 범위를 잘라 확대하고, 로봇을 중앙의 빨간 방향 표시로 그린다.
- 이미지를 JPEG로 압축하고 `!IHHI` 12바이트 헤더와 청크로 전송한다.
- 현재 UDP 페이로드에는 원본 격자의 resolution·origin·좌표계·로봇 pose·센서 시각이 구조화된 데이터로 들어 있지 않다.
- `self.mapper.pose`에 위치·방향 추정값은 있으나 별도 ROS pose/TF 또는 UDP pose 출력은 이 구현에 없다. 추가로 노출해야 한다.
- 미니어처를 이미지 색상으로 역추정하기보다 `/map` 원본과 pose를 보내는 편이 정확하다. JPEG 손실, 색상 임계처리, 잘라내기, 화살표 표시가 원본 정보를 바꾸기 때문이다.

현재 `quest_v2.launch`는 조종·카메라·선택 상태 송신만 실행하며 라이다 드라이버나 매핑 노드를 포함하지 않는다. 지도 기능은 별도 실행·통합이 필요하다. 구형 `run_vr.sh` 전체를 함께 실행하면 5005 조종기도 동작할 수 있으므로 매핑 전용 구성을 사용해야 한다.

근거: [Noetic 지도 코드](https://github.com/Ksyear/Puppy-PI-Cpp/blob/6648399fb612db1cfee4b35349fc12afaeb770a5/noetic_fallback/puppy_vr_control_noetic/scripts/lidar_mapping.py), [매핑 전용 실행 구성](https://github.com/Ksyear/Puppy-PI-Cpp/blob/6648399fb612db1cfee4b35349fc12afaeb770a5/noetic_fallback/puppy_vr_control_noetic/launch/lidar_mapping.launch), [Quest v2 실행 구성](https://github.com/Ksyear/Puppy-PI-Cpp/blob/6648399fb612db1cfee4b35349fc12afaeb770a5/puppypi_remote_camera/launch/quest_v2.launch).

### ROS2 지도 경로

- `src/lidar_mapping_cpp/`: LD19 LaserScan으로 2D 격자를 만들며 `map → base_footprint` TF를 발행한다.
- `src/puppy_vr_control/src/map_udp_sender.cpp`: `/map`을 회색조 PNG로 바꿔 UDP 5008로 전송한다. 역시 이미지 외 지도 좌표 메타데이터는 전송하지 않는다.
- `tools/vr_test_dashboard.py`: UDP 5008 청크를 조립해 화면 하단의 LiDAR MAP 패널에 표시한다.

ROS1은 JPEG·로봇 중심 표시, ROS2 송신기는 PNG·전체 격자 표시다. 포트가 같아도 이미지 내용과 좌표 의미는 다르다. 기존 송신기는 한 클라이언트 주소만 보관하므로 노트북과 Quest가 동시에 hello를 보내면 마지막 클라이언트로 목적지가 바뀔 수 있다.

저장소에 depth camera 실행 파일과 RTAB-Map RViz 설정도 있다. 특히 `src/slam/rviz/rtabmap.rviz`에는 `rtabmap_rviz_plugins/MapCloud`(XYZ·RGB8, `/mapData`)와 `MapGraph`(`/mapGraph`)가 정의되어 있다. 실제 사용자 스크린샷과 관련됐을 가능성은 있지만, 이 토픽이 실행 중이거나 `/mapData`가 표준 PointCloud2라고 단정하면 안 된다. 설정은 RTAB-Map 플러그인이 해석하는 형식이며 실제 발행 메시지 타입을 확인해야 한다.

`depth_camera.launch.py`에는 Dabai 분기가 있지만 해당 분기에서 참조하는 `include/dabai_dcw.launch.py`는 현재 checkout에서 찾지 못했다. 따라서 설정 파일 존재만으로 완성된 3D 실행 경로나 센서 장착 여부를 판단할 수 없다. 현재 Quest 경로에서 확인한 카메라는 JPEG 영상이며 깊이 데이터 전송은 없다.

근거: [ROS2 매핑](https://github.com/Ksyear/Puppy-PI-Cpp/blob/6648399fb612db1cfee4b35349fc12afaeb770a5/src/lidar_mapping_cpp/src/lidar_mapping_node.cpp), [지도 이미지 송신](https://github.com/Ksyear/Puppy-PI-Cpp/blob/6648399fb612db1cfee4b35349fc12afaeb770a5/src/puppy_vr_control/src/map_udp_sender.cpp), [대시보드](https://github.com/Ksyear/Puppy-PI-Cpp/blob/6648399fb612db1cfee4b35349fc12afaeb770a5/tools/vr_test_dashboard.py).

## 4. 권장하는 콕핏 표현

### 실제 스크린샷에 맞춘 3D 점군 연동 — 우선 검토

```text
현재 사용 중인 3D 지도 생성 프로그램
  → 점군 원본(x,y,z 및 색상) + 로봇/카메라 pose
  → 전송 브리지(밀도·범위·갱신량 제한)
  → Unity 점군 렌더러
  → 콕핏 내부의 축소 3D 지도
```

원본을 받아 콕핏 위 축소 지도, 확대·회전 가능한 지도, 로봇 위치 표시로 사용할 수 있다. 먼저 점 형태를 그대로 표현하면 되며, 표면을 연결한 메시 생성은 필수 조건이 아니다. 화면 스크린샷이나 영상만 전송하면 사용자가 다른 각도에서 보는 3D 지도는 얻을 수 없다.

필요한 정보는 다음과 같다.

- 생성 프로그램과 실제 실행 장치(로봇 Pi인지 외부 PC인지), 센서 모델.
- 원본 출력: ROS라면 실제 토픽 이름과 메시지 타입. `PointCloud2`는 후보이며 단정하지 않는다. 저장된 PLY/PCD만 있다면 정적 표시에는 쓸 수 있지만 실시간 출력 경로는 추가 확인한다.
- 점군 좌표계·단위, XYZ·색상 필드, 시각, 로봇/카메라 pose와 센서 장착 변환.
- 한 번에 보내는 점 수와 주기, 전체 누적 지도인지 신규 관측/변경 영역인지, 지도 최적화 때 기존 점·위치가 수정되는지.

지도 전체를 계속 누적해서 보내면 전송량이 증가한다. 예를 들어 XYZ float32 12바이트 + RGBA 4바이트로 패킹한다고 가정하면 10만 점은 헤더·압축 제외 1.6MB, 이를 초당 10회 보내면 16MB/s다. 실제 PointCloud2의 point_step은 이와 다를 수 있다. 초기에는 다운샘플링·주변 영역 제한·새로 바뀐 지도 블록만 전송하는 방식을 검토한다.

초기 검증은 대표 점군 한 장을 Unity/Quest에 표시하여 밀도·프레임 시간을 측정하고, 이후 실시간 스트림으로 바꾼다. SLAM이 과거 위치를 보정하면 이전 점군 블록도 교체하거나 변환해야 하므로 단순히 새 점을 계속 추가하는 구현으로 끝내지 않는다.

프로토타입 연결 후보로 Unity의 ROS-TCP-Connector를 검토할 수 있지만, 현재 Unity 6·Quest 빌드·실제 메시지 타입과의 호환성과 성능은 별도 검증해야 한다. 최종 지도 채널은 이동 제어 UDP 5001과 분리하고, 큰 데이터가 조종 패킷 처리를 막지 않게 구성한다.

참고: [ROS PointCloud2 정의](https://github.com/ros2/common_interfaces/blob/rolling/sensor_msgs/msg/PointCloud2.msg), [Unity ROS-TCP-Connector](https://github.com/Unity-Technologies/ROS-TCP-Connector).

### 2D 라이다를 활용할 때의 대안

콕핏 안에 축소된 지도 판을 두고, 관측한 빈 공간은 바닥, 장애물은 일정 높이의 벽·기둥, 미탐사 구역은 별도 색으로 표시한다. 로봇 모형이나 화살표는 지도상의 추정 위치·방향을 따라 움직인다. 사용자는 고개를 움직여 옆에서 보거나 확대·회전할 수 있다.

현재 스캔 점은 누적 지도와 다른 색으로 표시하면 움직이는 주변 물체와 과거 지도 정보를 구분하기 쉽다. 단, 현재 코드에 독립된 동적 물체 추적·분류가 구현됐다는 뜻은 아니다.

로봇 측은 센서 처리·위치 추정을 맡고, Unity는 데이터를 받아 기하와 재질을 만든다. 로봇에서 RViz 화면을 렌더링해 영상으로 보내는 방식으로는 사용자의 시점에 맞춰 지도 주변을 자유롭게 볼 수 없다.

## 5. 추가로 합의할 데이터

이동 제어 v2 패킷은 그대로 유지하고 지도·위치 데이터는 별도 채널로 보낸다. 다음은 필요한 정보 목록이며 아직 확정된 wire 규격이 아니다.

| 데이터 | 최소 정보 | 초기 전송 목표(측정 후 조정) |
|---|---|---|
| 지도 | map_id, revision, width/height, resolution_m, origin 위치·방향, frame_id, 점유값(-1/0~100), 마지막 반영 센서 시각 | 현재와 같은 1Hz에서 시작, 필요 시 2~5Hz 또는 변경 영역 |
| 로봇 pose | map_id, sequence, 동일 좌표계의 x_m/y_m/yaw_rad, 측정 시각, 유효 상태 | 센서·추정 갱신에 맞춰 5~10Hz 목표 |
| 선택: 현재 스캔 | 각도·거리 배열 또는 평면 점, 센서 장착 변환, 측정 시각 | 실제 스캔 주기 이내 |

Noetic에서는 map과 pose를 같은 잠금 구간에서 일관되게 복사해 전송하고, 로봇을 재시작하거나 지도를 초기화하면 map_id를 바꿔 이전 좌표 데이터와 섞이지 않게 한다. ROS 좌표는 x 전방/y 좌측/z 위, Unity 표시를 x 우측/y 위/z 전방으로 정하면 위치 변환은 `(-ROS.y, ROS.z, ROS.x)`이며 회전도 같은 기준으로 변환해야 한다.

전송 시각과 마지막 센서 갱신 시각을 구분해야 한다. 현재 매핑 타이머는 스캔이 끊겨도 기존 지도를 다시 송신할 수 있으므로, 수신이 계속된다는 이유만으로 새 관측이라고 표시하면 안 된다. 로봇 재시작, 지도 초기화, 추정 실패, 센서 끊김을 UI에서 구분한다.

점유격자는 압축된 바이트 배열로 전송하는 편이 적합하다. 기본 240×240 int8 격자는 압축 전 57,600바이트라 단일 UDP 패킷으로 보내지 말고 청크 조립 또는 별도 신뢰성 있는 스트림을 사용한다. UDP를 쓰면 길이·크기 상한, revision, 청크 번호, 조립 만료 시간을 검사하고 완성된 최신 지도만 교체한다. 변경 영역만 보낸다면 누락 시 전체 지도 재동기화도 필요하다.

## 6. 실시간 표시와 성능

- 지도 갱신이 1Hz여도 VR 화면은 기기의 렌더링 주기에 맞춰 계속 그릴 수 있다. 두 주기를 같은 값으로 만들 필요는 없다.
- 위치·방향 갱신은 지도보다 자주 받고 짧게 보간할 수 있다. 보간은 실제 지연이나 추정 오차를 없애지는 않는다.
- 격자마다 독립 GameObject를 생성하기보다 지도 블록별 메시 또는 인스턴싱으로 표시하고 변경 영역만 갱신한다.
- 네트워크 수신·압축 해제와 Unity 오브젝트 갱신을 분리하고, 대기열은 최신 상태를 우선한다.
- 영상·지도·조종을 함께 사용할 때의 Quest 프레임 시간, Pi 부하, Wi-Fi 지연은 실측해야 한다. 이번 코드 검토로 프레임레이트나 통신 지연을 보장하지 않는다.
- 현재 자체 지도작성은 루프 클로저가 없는 스캔매칭이며, 보행 흔들림과 위치 추정 오차에 영향을 받는다. VR에서 입체적으로 보이더라도 측량 수준의 정확도를 가정하지 않는다.

## 7. 구현 순서 제안

1. 스크린샷을 만든 프로그램·센서·실행 장치와 원본 점군 출력 형식을 담당자에게 확인한다.
2. 대표 점군을 Unity에서 표시해 색상·좌표·축척과 Quest 표시 성능을 확인한다.
3. 원본 점군 및 pose 실시간 송신을 붙이고, 전송량과 갱신 방식에 맞춰 최적화한다.
4. 2D 지도도 병행한다면 위에서 확인한 UDP 5008 이미지 또는 격자+pose 경로를 별도로 연동한다.
5. 실측 후 갱신 주기·지도 범위·표현 밀도·지연 표시를 조정한다.

이번 작업에서는 Unity와 로봇 제어 코드를 수정하지 않았으며 실제 로봇·센서·Quest는 실행하지 않았다.
