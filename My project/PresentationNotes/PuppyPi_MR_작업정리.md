**PPT 제작용 작업 정리: Quest 3 기반 PuppyPi MR 조작 인터페이스**

정리 기준: 2026-10-04 대화까지. 사용자가 제공한 이전 Codex 대화 파일 `C:/Users/User/Desktop/작업내용`, 프로젝트 구현·검증 문서, 현재 코드, 이번 대화의 장치 확인 결과를 함께 반영했다. 아래 내용은 PPT에 옮길 원고이며 실제 PPTX 파일은 아니다.

발표의 중심은 MR 입력 인터페이스와 제어 통신, 안전 동작, 검증 결과다. 자동 검색과 원격 설치 문제는 부가 작업으로 짧게 설명한다. BallGrip 등 이전 대화 시작 전에 존재하던 구현은 프로젝트 문서와 코드를 근거로 포함했다.

**발표용 핵심 설명**

“Quest 3에서 사용하는 BallGrip 조작 인터페이스와 PuppyPi용 UDP v2 통신·안전 로직을 구현하고, 로컬 자동화 테스트로 동작을 검증했습니다. Quest Link 화면 출력 문제를 해결했으며 실제 Pi의 검색 응답도 확인했습니다. 실제 로봇 제어는 Pi의 실행 환경과 서버 구동을 확인한 뒤 검증할 예정입니다.”

**슬라이드 1. 프로젝트 목표와 개발 범위**

- Quest 3의 MR 공간에서 가상 조이스틱을 잡고 PuppyPi의 전후 이동과 회전을 제어하는 인터페이스 개발
- 손잡이 조작을 정규화된 제어 입력으로 변환하고 로봇 서버와 통신하는 구조 구현
- 손 놓기, 추적 상실, 통신 중단 시 제어 입력을 중립으로 전환하는 안전 동작 구현
- 이번 단계의 성과는 소프트웨어 구현과 로컬 검증, Quest 화면 출력 복구, 실제 Pi 검색 응답 확인

발표 설명: 전체 로봇 시스템 완성이 아닌, MR 제어 인터페이스와 통신 기반의 개발 현황을 보고한다. 실제 보행 시연은 아직 수행하지 않았다.

**슬라이드 2. 시스템 구성**

| 구성 요소 | 역할 | 현재 확인 범위 |
|---|---|---|
| Quest 3 | MR 화면 표시, 손·컨트롤러 입력 | 유선 Link 화면 출력 문제 해결. 실제 잡기 품질과 전체 조작 시나리오는 추가 확인 필요 |
| PC의 Unity | BallGrip 물리·입력 처리, 상태 표시, UDP 통신 | 코드 구현 및 EditMode·PlayMode 검증 |
| Pi 검색 서비스 | 같은 LAN의 검색 요청에 응답, 제어 서버 주소 안내 | 실제 Pi에서 실행 및 PC의 검색 응답 수신 확인 |
| Pi 조종 서버 | UDP v2 명령 수신, ACK 반환, ROS 제어 연결 | 로컬 파서·상태기 검증. 실제 Pi의 UDP 5001 서버는 미실행 |

발표 설명: 현재 시험 구성에서는 Unity가 PC에서 실행된다. Quest는 유선 Link를 사용하고 Pi와의 UDP 통신은 PC가 담당한다. Quest 단독 APK 배포는 이번 검증에 포함하지 않았다.

**슬라이드 3. BallGrip 2축 조작 인터페이스**

- 기존 단일 축 HingeJoint 기반 조작을 ConfigurableJoint 기반 2축 조작으로 변경
- 손잡이 기울기를 전후 이동과 회전 입력으로 변환하고 대각선 입력 지원
- 기본 최대 기울기 ±40°, 중립 구간 5°, 감도 및 축 반전 설정 제공
- 손잡이를 놓으면 입력을 즉시 0으로 만들고 물리 스프링으로 중립 자세 복귀
- 조종석 재소환 시 받침대와 자식 물리 객체의 상대 자세를 보존하고 입력 재활성화 조건 적용

발표 설명: Meta SDK의 잡기·놓기·취소 이벤트와 추적 상태를 연결했다. 손잡이의 비틀림은 이동 입력에서 제외한다. 구현과 로컬 시험을 완료했으며, 실제 Quest에서의 조작감·손 추적 품질은 별도 평가가 필요하다.

**슬라이드 4. UDP v2 제어 통신과 상태 표시**

- UDP 5001과 JSON v2 메시지 기반 클라이언트 구현
- 전후·회전 입력과 함께 세션 식별자, 순서 번호를 사용해 명령과 응답 관리
- ACK 수신 시 발신 주소·포트, 세션, 순서 번호, 응답 나이를 확인
- PC Game 화면과 Quest용 HUD에 입력·연결·서버 상태를 표시하도록 구현
- 기존 UDP 5005 송신기는 장면에서 비활성화하고 새 v2 송수신기를 사용하도록 정리

발표 설명: 송신했다는 사실만으로 연결 성공을 표시하지 않고 유효한 ACK를 확인하도록 했다. 실제 Pi의 조종 서버에서 ACK를 받는 단계는 아직 수행하지 못했다.

**슬라이드 5. 중립 전환과 재조작 조건**

- 손 놓기, 추적 상실, 앱 일시정지 및 포커스 상실 시 중립 명령 요청
- ACK가 끊기면 제어 세션을 차단하고 입력 중립 유지
- 추적·통신이 복구되어도 잡고 있던 상태로 자동 재출발하지 않도록 새 잡기 요구
- 비상정지와 명시적 해제, 연결 해제·재연결 중 비상정지 상태 유지 구현
- 로봇 상태기의 watchdog 만료 처리를 보완하는 별도 패치 작성 및 로컬 회귀시험

발표 설명: 현재 ACK timeout 0.30초는 시험 설정값이다. 실제 로봇이 0.30초 안에 물리적으로 정지한다고 검증한 결과는 아니다. 서버 패치는 로컬 복제본에서 시험했으며 Pi에 적용하지 않았다.

**슬라이드 6. Quest Link 화면 출력 문제 해결**

- 증상: Unity Play 실행 후 Quest에서 모래시계가 계속 표시됨
- 점검: 장치 인식, OpenXR 세션, USB 연결, 패스스루 로그, Game 화면과 일시정지 상태 확인
- 확인한 원인: Unity의 일시정지 버튼이 활성화되어 있었음
- 해결: 사용자가 일시정지를 해제한 뒤 화면 출력 문제가 해결되었다고 확인

발표 설명: USB 2 연결과 패스스루 초기화 오류도 관찰했지만, 이를 이번 모래시계 문제의 확정 원인으로 발표하면 안 된다. 패스스루 오류 자체의 해소 여부는 확인하지 않았다. Air Link 방법도 검토했으나 사용자는 유선 연결을 유지했다.

**슬라이드 7. 연결 편의 기능과 실제 LAN 검색**

- PC Unity Game 화면에 기기 검색, IP·호스트 이름 직접 입력, 연결·해제, 최근 기기 및 상태 표시 구현
- Play를 재시작하지 않고 다른 주소로 재연결하도록 연결 수명주기 개선
- Python 표준 라이브러리로 UDP 5002 검색 서비스와 systemd 서비스 파일 준비
- PC와 Pi를 같은 공유기 네트워크로 맞춘 뒤 Pi 검색 프로그램 실행
- PC 검사 도구에서 Pi의 유니캐스트·브로드캐스트 검색 응답과 기기 이름 `puppy` 확인

발표 설명: PC가 5GHz, Pi가 2.4GHz에 연결된 상태에서도 실제 통신을 확인했다. Pi 검색 성공은 조종 서버 연결 성공과 별개다. Unity의 검색 목록 화면에서 실제 표시되는지에 대한 사용자 확인은 기록에 없다. 부팅 자동 실행과 DHCP 주소 변경 후 재검색은 실제 장치에서 검증하지 않았다.

**슬라이드 8. 자동화 검증 결과**

| 검증 구분 | 최종 기록 | 주요 검증 내용 |
|---|---:|---|
| Unity EditMode | 34/34 통과 | 입력 변환, SDK 이벤트 연결, 세션·ACK 검증, 검색 응답 처리 |
| Unity PlayMode | 7/7 통과 | 물리 동작, 실제 loopback UDP, 연결 변경·재연결, 중립·비상정지 |

| 로봇 코드 및 패치 회귀시험 | 74/74 통과 | 실제 로봇 파서·상태기와 watchdog 처리, mock 기반 ROS 출력 경로 |

발표 설명: 자동화 테스트는 합계 119개이며 6개 메시지 왕복 확인은 별도로 제시한다. 이전 24개 EditMode·2개 PlayMode 기록은 최종 34개·7개에 포함되므로 다시 더하지 않는다. 결과는 기존 실행 기록에 근거하며 이번 정리 작업에서 테스트를 새로 실행하지 않았다. 모터와 실제 보행을 검증한 결과가 아니다.

**슬라이드 9. 실제 Pi 연동에서 확인한 제약**

- Pi 운영체제: Debian GNU/Linux 13 (trixie)
- 기존 조종 실행 스크립트는 ROS1 Noetic 환경을 전제로 작성되어 있음
- 현재 확인한 Pi 호스트에는 `/opt/ros`가 없고 `ROS_DISTRO` 출력도 없음
- Docker 조회 권한과 sudo 비밀번호를 확보하지 못해 컨테이너 내부의 ROS 설치 여부는 미확인
- UDP 5002 검색 서비스만 실행 중이며 UDP 5001 조종 서버는 미실행
- 작업용 SSH 키를 등록했으나 인증을 완료하지 못해 원격 점검 중단

발표 설명: “ROS가 전혀 설치되어 있지 않다”라고 확정하지 않는다. 호스트의 일반적인 설치 경로가 없고 Docker 내부를 확인하지 못했다는 것이 확인된 범위다. 저장소와 실행 파일은 존재하지만 실행 환경이 준비되었다고 볼 수 없다.

**슬라이드 10. 작업 범위 조정과 다음 단계**

- 자동 검색과 설치 편의 기능의 추가 작업을 보류하고 핵심 MR 조작 검증에 집중하기로 결정
- 이미 작성한 연결 UI와 검색 코드는 유지하며, 주소 직접 입력을 우선 사용하는 방향으로 정리
- Quest에서 실제 잡기·놓기·소환·추적 상실 동작과 HUD 가독성 확인 필요
- Pi 실행 환경과 조종 서버를 확보한 뒤 실제 ACK와 ROS 시험 출력을 확인할 계획
- 모터를 연결하는 단계에서는 통신 단절, 비상정지, 정지 후 재조작 조건을 실제 장치에서 확인할 필요가 있음

발표 설명: 부가 기능을 보류해도 Pi 조종 서버 실행은 실제 로봇 연동을 위해 필요하다. 고정 IP가 이미 설정되었거나 실제 제어가 완료된 것으로 표현하지 않는다. 기존 코드를 삭제하거나 되돌리지는 않았다.

운영 정리: PC의 임시 전송 서버들은 종료했다. Pi 검색 프로그램 종료와 작업용 SSH 키 제거는 사용자에게 안내했지만, 실제 수행 완료 응답은 기록에 없다. 추가 진단 스크립트는 PC에만 준비했고 Pi에서 실행하지 않았다. 이 운영 상세는 발표 본문보다 필요할 때 참고하는 자료로 두는 것이 적절하다.

**발표 보충 자료: 수치와 용어**

- 입력 축: `forward`, `turn`, 각각 정규화된 -1~1 범위
- 기본 기울기 제한: ±40°, deadzone 5°, 감도 1
- 일반 명령 송신: 평균 20Hz 구현, 실제 무선 환경의 처리율 측정값은 아님
- 현재 ACK timeout: 0.30초, 허용 ACK 나이: 0.20초, 시험용 설정값
- 로컬 시험 입력 예: `(forward=0.6, turn=-0.3)`일 때 `x=3 cm/s`, `y=0`, `yaw=-0.06 rad/s`
- 위 전진 속도의 SI 환산: `0.03 m/s`. 실제 로봇에서 측정한 속도가 아닌 파서·변환 로직 시험 결과
- 제어 포트: UDP 5001. 검색 포트: UDP 5002. 기존 UDP 5005 구현과 구분
- 검색 범위: 동일 LAN. 서로 다른 장소의 인터넷을 연결하는 원격 접속 기능은 구현 범위 밖

**발표 구성 제안**

10장 구성에서는 MR 입력과 통신·안전 구현에 가장 많은 설명 시간을 배정한다. 자동 검색은 슬라이드 7 한 장, 배포 제약은 슬라이드 9 한 장으로 설명하면 된다. 짧은 발표에서는 슬라이드 1과 2, 슬라이드 4와 5를 각각 합쳐 8장으로 줄일 수 있다.

화면 자료를 넣을 때는 실제 Unity 장면, 입력·상태 UI, 검증 결과표를 사용한다. 현재 보유하지 않은 실제 로봇 보행 화면이나 측정 그래프를 성과 이미지로 만들지 않는다.
